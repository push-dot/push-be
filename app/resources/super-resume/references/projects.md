# 프로젝트 설명 구성

## STAR 구조
Situation → Task → Action → Result 순서. 개발자 이력서에서는 Action과 Result를 중심에 둔다. Situation은 프로젝트명이나 도메인명으로 대체 가능하다.

## 수치화
실사용자가 없어도 부하 테스트로 측정값을 만들 수 있다. 단일 컨테이너 k6 측정값도 유효한 데이터다.

## 단순 구현 보강
"로그인 구현" → "OAuth 기반 로그인 도입으로 가입 흐름 단축"처럼 왜 구현했고 어떤 효과가 있었는지를 한 문장으로 붙인다.

## 기술 선택
기술명 나열보다 선택 기준과 트레이드오프를 쓰는 쪽이 더 강력하다. "Redis 사용"보다 "Local cache 대비 Redis를 선택한 이유"가 낫다.
