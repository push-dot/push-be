# AUDIT_NOTES — core-a

Changes needed outside the core-a area, found while auditing `services/core-api` auth, billing, companies, conversations and notifications.

| # | Severity | File:line | Problem | Proposed fix |
|---|----------|-----------|---------|--------------|
| 1 | High | `services/core-api/src/jobs/credits.ts:11-16`, and every `billing_ledger` writer (`billing/credits.ts:29-30`, `routes/billing.ts` `userLedger`/`companyLedger`/checkout CTE) | Balance is the `balance_after` of the latest ledger row, and each insert computes `balance_after` from a subquery. Two concurrent grants (webhook + monthly grant on `GET /billing`) read the same last balance, so one grant is lost. READ COMMITTED snapshots make an advisory lock inside the same statement unreliable. | Derive the balance as `SUM(amount_micro_credits)` per owner in `availableMicro` and keep `balance_after` as display only. Or serialize writers with `SELECT ... FOR UPDATE` on the owner row in one transaction (needs a transaction-capable driver, not Neon HTTP single statements). |
| 2 | Medium | `README.md:203-204,331`, `.env.example:82`, `infra/vps/env.example:43`, `docs/plans/2026-10-21-fo-web-employer-api.md` decision 52 | `APPLE_IAP_KEY` is no longer read. Device `POST /billing/iap/verify` for APP_STORE now verifies the StoreKit 2 `signedTransaction` locally (x5c chain to `APPLE_ROOT_PEM`) and requires the new `APPLE_BUNDLE_ID` (503 `NOT_CONFIGURED` when unset). | Replace `APPLE_IAP_KEY` with `APPLE_BUNDLE_ID` in both env examples and the README table, and update decision 52 ("Device verifyApple still calls the StoreKit API" is no longer true). |
| 3 | Medium | `README.md:203`, deploy secrets | Google Play `verifyGoogle` sends `GOOGLE_PLAY_KEY` as a static bearer. Android Publisher needs a short-lived OAuth token from a service account, so a static value expires within an hour. Subscriptions now use `purchases/subscriptionsv2`. | Mint the access token from a service-account JWT per request (or cache it for its lifetime) instead of a static secret. |
| 4 | Medium | `services/core-api/src/billing/stores.ts` `decodeGoogleNotification` (core-a area, design is documented as decision 52) | Real Play RTDN Pub/Sub pushes carry base64 JSON, not a JWS, and the OIDC key is pinned instead of fetched from Google's JWKS. The path fails closed, so Google webhooks never grant. Not changed because it is a documented decision. | Product decision: accept the unsigned Pub/Sub JSON after OIDC verification against Google's JWKS (with the `exp` check added in 37c1e9a), then re-verify state with `subscriptionsv2`. |
| 5 | Medium | `services/core-api/src/routes/conversations.ts` `allowChat` | The monthly managed-AI limit and `ultraResume` plan check run only when the client sends `ai`. Omitting `ai` skips them on the postgres queue path, and enforcement then depends on the worker. The redis path reserves credits in `jobs/enqueue.ts`. | Confirm the Python chat worker enforces credits when `ai` is null (`services/ai/src/app/queue/credits.py`). If it does not, run the usage check for every message. |
| 6 | Low | `services/core-api/src/ratelimit.ts:35-48` | Windows are fixed at 60 s, so the new per-email login limit (10/min) still allows about 14k guesses a day per account. | Add a `windowSec` parameter (bucket = `floor(now / windowSec)`, `expires_at` = window end) and use an hourly/daily login bucket alongside the per-minute one. |
| 7 | Low | `services/core-api/src/handler.ts:231` (core-a) and the upload routes in other areas | `idempotent()` buffers the whole POST body before dispatch, so a body up to the Workers limit (100 MB) sits in memory twice. The core-a PDF route now rejects a large `content-length` before parsing the form. | Optionally cap `content-length` in `idempotent()` at the largest upload any route accepts. |
| 8 | Low | `services/core-api/src/routes/email-auth.ts` signup | Pre-hijack risk inherent to link signup: anyone can start a pending signup for an address, and if the owner clicks that link the account gets the attacker's password. Mail is now limited per address, but the design risk remains. | Ask for the password again at verify, or send a "someone tried to sign up" notice when a pending row is replaced. |

Data note: Google IAP claims and ledger references used `orderId`. They now use the purchase token, which is the id the webhook looks up. Google rows verified before this change keep `orderId` and still won't match webhooks, the same as before.
