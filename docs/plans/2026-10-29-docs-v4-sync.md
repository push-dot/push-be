# push-be: workspace docs v4 sync plan (2026-10-29)

Goal: implement every "API 변경 필요" item in the workspace docs (push-workspace `docs/*.md`, develop @ b505d45) in push-be, so the server matches the docs and the mobile Claude Design v4.

## Ground rules
- Repo: push-be only. Do not touch push-fe, push-workspace docs, or fo-desktop.
- Package managers: push-be uses **npm** workspaces (package-lock.json) for TS and its existing Python tooling for `services/ai`. Never run pnpm/bun/yarn here, and never chain package managers with `||`.
- Follow coding-hooks conventions: `coding-hooks:backend`, `coding-hooks:solid-layers`, `coding-hooks:git`.
- One branch and one PR per task, base `develop`. Branch `feat|fix|refactor|chore/<kebab>`; commit/PR title `type(scope): summary` (English, scope required, under 72 chars). Do NOT merge PRs. Stack later tasks on develop, not on each other, unless a task truly depends on an earlier one; if so, say so in the PR body.
- Contracts first: update `packages/contracts/spec/*.ts`, regenerate (`npm run contracts`), then server code, then tests. New DB columns go in a new migration `db/migrations/0026_*.sql` and up (never edit old migrations).
- Every task: tests added or updated, `npm run typecheck` and `npm test` pass (and the ai service's tests if touched). Paste the commands and the pass summary in the PR body.
- Write no secrets. Apple keys and the SMS provider come from env vars, documented in the README and `.env.example` if one exists.

## Tasks

### T1. Remove BYOK (`chore/remove-byok`)
- `credentialMode` accepts `MANAGED` only. Remove `BYOK` from contracts, core-api (`types.ts`, `routes/integrations.ts` AI-key storage and listing), gateway, and the ai service (`config.py`, `worker.py`). Remove the `INTEGRATION_REQUIRED` path that comes from a missing BYOK key. Keep `INTEGRATION_REQUIRED` for Google integration.
- Remove or adjust the BYOK tests and parity fixtures. If a DB table only stores AI keys, drop it in a new migration. Otherwise leave the data and stop reading it, and note that in the PR.

### T2. Contract cleanups (`refactor/contracts-docs-v4`)
- `POST /auth/email/signup`: `accountType` takes `EMPLOYER` only, so reject `PERSONAL`. Remove `consentReference`.
- `POST /billing/checkout`: `planId` is employer `BASIC|PRO|ULTRA` only, and the caller must be an employer admin (403 otherwise). Personal `PRO|ULTRA` is rejected, because personal accounts pay in-app only.
- Settings: remove `chatRetentionDays`, `defaultEffort`, `confirmBeforeEdit`. Keep `aiAccessMode` (`ALWAYS_ASK|AUTO|BYPASS`, default `AUTO`).
- Message requests: the server decides `ai.effort` from the plan (FREE `LOW`, PRO `MEDIUM`, ULTRA `HIGH`). It ignores a client value, or rejects it if that is the existing style; pick one and document it in the PR.

### T3. Document kind and profile counts (`feat/career-statement-and-profile-counts`)
- Add a 경력기술서 kind to the document `kind` enum. Suggested value: `CAREER_STATEMENT`. Check the ai service for kind handling and update prompts and templates if they switch on kind.
- `Profile` gains `followingCount` and `postCount` next to `followerCount`. Compute them from existing follow and post tables.

### T4. Conversation archive and delete (`feat/conversation-archive-delete`)
- `DELETE /conversations/{id}` (owner only): delete or soft-delete, matching the existing deletion style. Cascade or hide messages, jobs, and approvals as the schema needs.
- Archived list: `GET /conversations?archived=true`. The default still excludes archived conversations.
- Unarchive: an endpoint that mirrors the existing archive endpoint (e.g. `POST /conversations/{id}/unarchive`, or `PATCH archived:false` if archive is a PATCH). Follow the existing pattern.

### T5. Consents (`feat/agent-consent-and-terms`)
- Reference-data consent gate: for personal users with `user_consents.reference_data = false`, `POST /conversations` and `POST /conversations/{id}/messages` return 403 with a new error code (suggested `CONSENT_REQUIRED`). Employer conversations are not gated. Add the code to the shared error enum and to api-spec-style docs in the contracts.
- Signup terms: store the required terms (age 14+, service terms, privacy collection and use) and the optional 혜택·이벤트 알림, with agreed-at timestamps and terms version. Extend `GET/PUT /me/consents`, or add a dedicated endpoint, whichever fits the existing contract. Write a new migration for the columns. Required terms cannot be turned off; the optional marketing flag can.

### T6. Personal phone auth (`feat/phone-auth`)
- `users.phone` (E.164, unique among personal accounts) in a new migration.
- Endpoints: send code and verify code. Verify either logs in or creates the personal account, or links the phone to the account created right after an OAuth login. One phone maps to one personal account. Google, Apple, GitHub, and phone sign-in for the same number all land on the same account.
- 6-digit code, a resend cooldown (design shows a "2:48" countdown, so use a configurable cooldown), expiry, and attempt limits. Store codes hashed.
- Distinct error codes for a wrong code and an expired code (suggested `PHONE_CODE_INVALID`, `PHONE_CODE_EXPIRED`), plus rate-limit and duplicate cases.
- SMS sending goes behind an interface (infrastructure layer). The provider is undecided, so ship a dev/test sender that logs the code (never in production; guard it by env) and leave the real provider as a TODO in the PR.

### T7. Apple login (`feat/apple-login`)
- Web and Android: add `apple` to the `GET /auth/{provider}/start` provider enum and its callback, following the existing Google/GitHub OAuth PKCE flow. Apple uses `response_mode=form_post`, so handle a POST callback.
- iOS native: a new endpoint that accepts the Apple identity token (and nonce) from `expo-apple-authentication`, verifies it against Apple's JWKS (issuer, audience = bundle id, expiry, nonce), and returns the same Session shape.
- Apple may return a private-relay email. Do not merge accounts by email. The phone number identifies personal accounts (T6). New Apple users go through the phone step like Google and GitHub users.
- Config via env (team id, key id, client ids, private key). Tests use a locally generated key and a mocked JWKS.
